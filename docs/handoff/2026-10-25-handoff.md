## 0. 一页速览（先看这一节，再决定读哪）

### 0.1 这个项目在做什么

用户有两个现成的本地项目，想让它们合起来做一件事：**让大语言模型真的去"打"《七圣召唤》（Genius Invokation TCG）这盘棋**。

- `genius-invokation-dev/`：**游戏本体**（上游 piovium/genius-invokation 的本地分支 `local`），带一个"AI 对战场"（`#arena` 页面）。它的设计很关键：**对局跑在浏览器里，Node 只做静态文件服务与桥接（HTTP + SSE）**；"AI 玩家"的真正含义是"某个座位的 `PlayerIO` 由外部进程实现"。
- `1023 - 副本/vmaf_system/`：**VMAF**，一个自研的"可视化 DAG 工作流引擎"——节点=插件，连线=数据流，一次 `/run` 跑完一张图。用户希望用它来编排"LLM 怎么决策"。
- `driver/`：**我在两个项目之外新写的一层**，一台"司机"：把游戏桥接里冒出来的"该你出牌了"接住，喂给 VMAF 的图，再把图算出来的响应提交回游戏。

也就是说：**游戏负责规则与画面，VMAF 负责"策略编排"，司机负责时序与容错。** 三者用 HTTP/SSE/JSON 解耦，没有一个是"嵌在另外一个里面"的。

### 1.1 用户最初的目标

- 让两个项目**整合**（工作目录就叫"整合2。0"），并且"能发给别人一键跑"。
- 后来逐渐收敛成一条主线：**让 LLM 参与游戏**（用户 m00054 原话："最后的预期确实是想让LLM参与游戏"）。
- 用户对模块化的要求（m00056）：**模块要泛用、为这个任务写但要留出未来扩展的接口、要能在网页上拖拽拼接**。
- 用户想自己写提示词（m01073、m01962、m02587 反复强调）：**我只负责留槽位与工具，策略文字由他本人调试**。
- 演示需求：要能在网页上"看着两个 AI 打"，并且能看到"AI 在想什么"。

### 1.2 硬约束（改动前必须知道）

- **原版行为不能变**：不勾任何新开关时，游戏行为与上游一致。为此所有新开关默认值都是"关"或"等价于原版"（回合上限 `undefined` 时不传 `maxRoundsCount`；弹窗默认策略按模式决定；预设/让过/耗时间默认全关）。
- **不改上游卡牌实现**，不做"任意技能脚本编辑"。
- **只监听 127.0.0.1、无鉴权**：这是本地工具，不要暴露公网。
- **`genius-invokation-dev` 的 git 必须保持可合并**：`git remote` 指向上游，`local` 分支要能继续 `update-upstream`。目前工作区**有 4 个已修改文件未提交**（见 13.3），这是有意为之还是遗留，见该节说明。
- 用户的端口：`7717` 是他自己的另一个副本（`TCG1/genius-invokation-main/.../dist`），`8000` 是他 15:37 起的旧 VMAF（只有 12 个节点）。**这两个不要动**。我们自己用 `7807 / 8100 / 7810 / 5173 / 9344`。

### 1.3 两个项目的关键背景（不读会踩坑）

**游戏侧（genius-invokation-dev）**

- 引擎在浏览器：`window.theGame` 只在主页面存在；`#arena-board-*` 那个"对方棋盘"弹窗**只是显示客户端**，靠 `postMessage` 收 `notify` 渲染，没有 `theGame`。所以"弹窗卡住/进度不一样"**不影响对局**，但会误导观看者。
- "AI"= 该座位的 `PlayerIO` 由外部实现（`createAgentSeatIo`）：页面把 rpc 转成一次 HTTP 长轮询 `POST /api/arena/agent/request`，桥接生成 pending + deadline，往 SSE 推 `request` 事件；外部进程 `POST /api/arena/agent/respond`。**页面侧没有 422 重试循环**，重试只能由外部 driver 做。
- 页面超时会自己用默认响应过掉（action→宣布结束；chooseActive/selectCard→第一个候选；reroll/switchHands→空）。所以"driver 挂了"不会卡死，只会**看起来很傻**。
- 座位身份**只能由 SSE 的 `?seat=` 声明**：`/agent/respond` 体里没有 seat，服务端按 `pending.seat` 归属。连错座位的表现是"永远收不到请求"，或者"替人类下棋"。**用户上一轮就是卡在这里**（m00086 原话），所以我做了 `seatSelfCheck`（硬失败 `exit 3`）。

**VMAF 侧**

- 一次 `/run` 跑完一张图，**节点是纯函数**（`BaseNode.execute(inputs, context)` 不许跨调用存状态），所以它**不能自己等事件、不能常驻**——这就是为什么必须有"司机"这一层。
- `RunResponse` 里**没有 `shared`**：`shared` 只进不出。所以"跨回合记忆"只能由司机保存、每回合重新塞进 `shared`。
- `params` 全部 `extra="forbid"`；**连线值覆盖静态参数**；解析期任何 error → `aborted`（一个节点都不跑）。
- 类型预检很严：`Dict[str,Any]` 不能接到 `str` 输入（这就是我为什么需要 `json_pick`、`shared_get` 这种"降维节点"）。
- 插件是**热更新**的：改 `.py` 后打一次 `/health` 就注册；`_NON_RELOADABLE_MODULES` 里的（契约层）不能热重载。
- 插件扫描是**测试夹具的一部分**：`tests/conftest.py` 里 `scanner` fixture 断言"扫描无错误"，所以任何一个插件语法/契约错都会让**全量测试**红。

### 2.2 一手决策的完整时序（这是最重要的那张图）

```
游戏引擎轮到 AI 座位
  → seatIo.ts: requestEvent(生成 aiDetail) + flushAiEvents()
  → requestDecision({matchId, seat, request, state, timeoutMs, aiDetail})
  → bridge: id = nextPendingId++, deadline = now + clamp(timeoutMs, 1s, 600s)
  → SSE: event: request  {id, matchId, seat, request, state, deadline, aiDetail}
driver 收到：
  1) 去重（同 id 只处理一次；reset 清空）
  2) budget = deadline - now - safetyMs(3000)；budget < 1500ms → 直接交默认响应
  3) shared = { request, state, aiDetail, meta{...remainingMs}, retry, ctx{summary},
                plan, deck, winrates, intent, config, catalog(按回合裁剪的名字表) }
  4) POST http://127.0.0.1:8100/run，HTTP 超时 = budget
  5) 从 results 里取"决策节点"（现在是 build）的 output.response
  6) checkShape(request, response) —— 本地镜像桥接的校验，形状不对就地兜底（防 GiTcgIoError 判负）
  7) POST /api/arena/agent/respond {matchId, id, response}
       200 → 记 ok，落盘 store.turn + live.turn
       422 → 把 {reason, validity, availableActions} 塞 shared.retry，重跑（最多 --max-attempts 次）
       404 → 已被默认应答/被别人答了 → 记 late，永久封存，不再提交
  8) 写会话 JSONL / 观测 JSONL；回合切换时顺手触发 review
```

### 2.3 为什么"驾驶"必须在外置进程

- VMAF 节点是纯函数、一次 `/run` 立即结束，**没有"等外部事件"的能力**；而游戏是长会话事件流。所以"谁一直等、什么时候跑一次"必须由一个常驻进程负责。
- 这个进程还必须是**唯一知道 `run_id ↔ request id ↔ deadline ↔ latency` 的人**，因为复盘、审计、观测都要这层信息。
- 结论（也是当时的决策依据）：**驱动与策略分离**——驱动不在 VMAF 里（`driver/arena-driver.mjs`），策略 100% 在图里（蓝图 + 插件）。这样"改策略只动图/插件，改时序只动 driver"。

## 4. 接口与契约（背下来能省一天）

### 4.1 游戏桥接（`local/arena/bridge.mjs`，前缀 `/api/arena`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/agent/stream?matchId=local&seat=N` | SSE。先 `: connected`，再 `event: hello {matchId,seat,aiSeq,status,pending[]}`（`status` 是**加入连接之前**的快照，所以自己的计数会滞后 1），随后可能补一条 `state`；每 15s 一条 `: keepalive` |
| POST | `/agent/respond` | 体 `{matchId, id, response}`，`response` 必须是**完整 RpcResponse**。返回 **200**（已采纳）/ **422**（非法，`pending` 保留，体里有 `reason/validity/availableActions`）/ **404**（没有这个 pending：超时了，或被别的连接答了） |
| POST | `/agent/request` | 页面用（长轮询），driver 不调 |
| GET | `/status` | `{agents{0,1}, pending{0,1}, pendingRequests[], decks{0,1}, startRequested, config, logCount, aiSeq}` —— **排错第一入口** |
| GET | `/state?seat=N` | `{seat, state}`；`state.phase === 5` 就是 `gameEnd`，`winner` 在 `state.winner` |
| GET | `/ai/log?seat=N&since=S&limit=L` | 结构化事件流；**实测只回最近 500 条**（`lastSeq` 可续读，但历史深处读不到），不能用来做逐请求审计 |
| GET | `/ai/snapshot?seat=N` | 最近一次 snapshot（开局 / 每回合末 / 结束） |
| GET | `/catalog` | 全量 id→名字/费用/技能表（155 角色 + 597 卡 + tokens + skills） |
| GET | `/card-text` | id→卡面文字 |
| GET | `/decks`、`/deck?seat`、`/prepare` | 牌组库 / 某座位牌组 / 开局准备度 |
| POST | `/deck` | 体 `{matchId, seat, name, characters:[id], cards:[id] 或 [{id,count}], note}`；校验 3 个不重复角色、30 张牌 |
| POST | `/state` | 页面推 `{matchId, seat?, state, config}`；**config 只有页面推过来才有值**（见 8.5） |
| POST | `/control` | `{action:"start"}` 让页面开局（无页面可操控时用不到） |
| POST | `/reset` | 清 pending/states/logs/decks/config，广播 `reset`；`nextPendingId` **不重置** |
| GET | `/log` | 最近 500 条操作日志（给人看的） |
| GET | `/spectate` | **含双方完整状态，会泄漏对手手牌/骰面**，只许调试 |

**SSE 事件**：`hello` / `state` / `request` / `ai_event` / `responded`（`{id}`，会广播给该座位**所有**连接，包括刚答完的那个）/ `timeout` / `reset`。

**`request` 事件载荷**：`{id, matchId, seat, request, state, deadline, aiDetail}`。
- `request` = protobuf 的 `RpcRequest` JSON：`{"request":{"$case":"action","value":{...}}}`。
- `state` = `ExposedGameState`：**自方完整，对方只有公开信息**（对方手牌 `definitionId` 一律 0，骰面不给）。
- `aiDetail` = 页面已经翻译好的"人类可读视图"，是给模型的主要输入。

### 4.2 五种 rpc 与响应形状（错一个就是 IO 错误判负）

| `$case` | 请求里的关键字段 | 响应的 `value` |
| --- | --- | --- |
| `action` | `actions[{index,kind,name,validity,cost,autoSelectedDice,preview[]}]` | `{chosenActionIndex, usedDice?}`（`usedDice` 可省，服务端会用该动作的 `autoSelectedDice` 覆盖） |
| `chooseActive` | `candidateIds[]` | `{activeCharacterId}` |
| `selectCard` | `candidateDefinitionIds[]` | `{selectedDefinitionId}` |
| `rerollDice` | `dice[]`（骰面语义）+ 重投次数 | `{diceToReroll: DiceType[]}` |
| `switchHands` | `hand[]` | `{removedHandIds: number[]}` |

**`validity`**：`0` 合法、`1` 条件不满足、`2` 没有可选目标、`3` 骰子不足、`4` 充能不足、`5` 被技能状态禁用、`6` 本局秘传已用。非 0 的项**不能选**。

**DiceType 有两套语义（最容易被搞混）**：
- 费用语义：`0=任意, 1..7=冰水雷火风岩草, 8=相同元素, 9=充能, 10=秘传`
- 骰面语义：`1..7=元素, 8=万能`

**`action` 的 `kind` 实测取值**：`useSkill`（普攻/战技/爆发）、`playCard`（出牌）、`elementalTuning`（**调和骰子**，弃 1 张手牌换 1 个指定元素骰）、`switchActive`（切人）、`declareEnd`（宣布结束回合）。
→ 所以"调和骰子"**是**给模型的（作为 action 的一种）；"重投"是**另一个 rpc**（`rerollDice`），只在掷骰阶段出现。

### 4.3 `state` 的真实形状（HANDOVER 里写的不对，以这里为准）

```jsonc
{
  "phase": 3,              // 0准备手牌 1选出战 2掷骰 3行动 4结算 5结束
  "currentTurn": 0,
  "roundNumber": 3,
  "player": [ /* 长度 2，下标即座位 */
    {
      "activeCharacterId": -101,          // 负数实例 id
      "character": [{ "id": -101, "definitionId": 1101, "defeated": false,
                      "entity": [], "health": 8, "maxHealth": 10,
                      "energy": 1, "maxEnergy": 3, "aura": 4, "tags": [] }],
      "handCard": [{ "id": -9, "type": 1, "definitionId": 330008, "definitionCost": [2],
                     "variableName": "", "variableValue": 0, "tags": [], /* ... */ }],
      "dice": [4, 8, 1],                  // 骰面值，不含中文
      "pileCard": [...], "combatStatus": [...], "support": [...], "summon": [...],
      "initiativeSkill": [...], "declaredEnd": false, "legendUsed": false, "status": 0
    }, { /* 对方：handCard 的 definitionId 全是 0（隐藏），dice 长度可见但值不保证 */ }
  ]
}
```

- `state` 里**没有任何中文名**，只有 `definitionId` → 必须靠 `/catalog` 翻译（`driver/lib/names.mjs` 干这个）。
- 角色身上的状态/装备也是 `entity`，例如 `{definitionId:123041, variableName:"shield", variableValue:5}`。

### 4.4 `aiDetail`（`request` 事件里那份"人类视图"）

顶层：`{type:"request", at, seat, rpc, round, phase, currentTurn, deadline, attempt}`。

`rpc === "action"` 时额外有：
```
actions: [{ index, kind, name, skillId?, validity, validityLabel,
            cost: { dice: { "0": 2, "3": 1 }, total: 3, text: "2火元素+1冰" },
            autoSelectedDice: [3, 1, 7],
            preview: [{ type: "damage", targetId: -500000, target: "对方出战",
                        amount: 2, element: "火", reaction: null, defeated: false }] }]
validActions: [...]   dice: [...]   diceLabels: ["火","万能","冰"]
declaredEnd: false    activeCharacter: {...}   disabledBy: [...]   note: ""
```
`chooseActive` 给 `candidates[{id,name,health,maxHealth}]`；`selectCard` 给 `candidates[{definitionId,name}]`；`switchHands` 给 `hand[entityView]`；`rerollDice` 给 `dice/diceLabels/note`（`attempt>0` 表示还有额外重投机会）。

> 注意：`cost.dice` 是**计数字典**不是数组。`action_menu.py` 里按数组渲染费用的分支对它是无效的，所以菜单只显示"费用 3"（这也是个待修的小问题）。

### 4.5 牌组分享码（`driver/lib/deckcode.mjs`）

- 算法与游戏 `packages/assets-manager/src/sharing.ts` 一致：base64 → **51 字节**；末字节是偏移 `last`，前 50 字节两两交错减 `last` 取低 8 位 → 25+25 重排 → 每 3 字节拆 2 个 12 位整数 → **33 个 id**（前 3 角色、后 30 行动牌）；再用 `share_id.json`（`genius-invokation-dev/packages/assets-manager/src/data/share_id.json`，597 项）做 shareId→id。
- 已验证互通：`FZDByRUNGRCB0WoNFlGgWpEPE0AB9TAPFGCB9kgWGIERCoEQDLFADcQQDPFgacYWDJAA` → `[1411, 2102, 1510]` + 30 张。
- 另一套：`FdHxNj8TAWDQxFkMFkAhyWIYCYDA45wOCUDQ5J0PGEAh9IIPGWDh9p4YC6FgirYRCxAA` → `[2304, 1311, 1404]`。

### 4.6 VMAF 侧

- `POST /run {blueprint, shared?, strict?, run_id?}` → **永远 200**：`{run_id, ok, aborted, abort_reason, total_ms, results[{node_id,node_type,ok,skipped,error,elapsed_ms,output}], errors, error_details}`。
  - `results[i].output` 是**模型实例**（Python 对象），不是 dict —— 在测试里要 `out.text` 而不是 `out["text"]`。
- `POST /validate {blueprint}` → `{valid, order, entry_nodes, exit_nodes, issues[]}`；先跑解析器：节点/边/类型/环/必填，**任何 error 就 aborted，一个节点都不跑**。
- `/schema` 给前端画节点；`/health` 给 `node_count` 与 `scan_summary`（改插件后打它一次即可热更新）。
- 类型预检规则（写蓝图时必须遵守）：`Any` 兼容一切；`Dict/List` 与 `str` **不兼容**；`int→float` 兼容，反之不兼容；源 `Union` 逐成员、目标 `Union` 任一兼容。
- 节点契约：`node_type`（=文件名）、`description`、`version`、`input_model`、`output_model`、`control_flow`、`async execute(inputs, context)`；`context` 是**只读视图**：`{run_id, node_outputs: {id: dict}, shared: dict}` —— **读 `context["shared"]` 就是和司机通信的唯一方式**。

## 5. 已实现的功能清单（按模块）

### 5.1 司机（`driver/arena-driver.mjs`，约 1300 行）

**四种模式**：`probe`（只看，不提交）/ `record`（连上就录音，什么都不答）/ `echo`（自己随便选一个合法动作）/ `vmaf`（跑蓝图）。

**关键参数**（`--help` 有全表）：
```
--seat 0|1                    座位（★ PvE 默认 AI 在 1；EvE 两个座位都要开）
--mode probe|record|echo|vmaf
--bridge http://127.0.0.1:7807
--vmaf   http://127.0.0.1:8100
--blueprint <path> | --blueprint-id <serverId>     # id 优先，每回合重新拉 → 改完下一手即生效
--prep-blueprint <path>   --review-blueprint <path>
--deck-code <分享码> | --deck <json>   --plan <text>   --no-prep   --no-review
--session <name>   --session-dir driver/sessions
--max-attempts 3   --safety-ms 3000   --min-budget-ms 1500
--exit-on-end <sec>   --show-menu   --no-payload   --log-file <path>
```

**已内置的工程能力**：
- 单飞队列 + `seen` 去重（`reset` 清空）+ 每手 deadline 看门狗。
- **座位自检**：每 2s 查 `/status`，若"别的座位有 pending 而本座位没有"或"别的座位有 agent 而本座位没有"→ 硬失败 `exit 3`（用户上次就是卡在这里，这个必须保留）。
- 蓝图路径解析 `resolveInput/resolveOut`：`--blueprint blueprints/decide.json` 这种相对写法先按 cwd，再按 driver 根目录找；输出路径同样归一到 driver 目录。
- 蓝图直连失败保护：若一次决策里 `ok==0 && fallback==0 && 错误含"蓝图不可用"` → `shutdown("蓝图不可用", 4)`，避免打出"整局全兜底"的假对局。
- 对局结束检测：每 3s 查 `/state`，`phase===5` 即结束（不能靠 `winner` 事件——它要等下一次请求才 flush，而结束时没有下一次请求了）；必须有 `sawRequest` 门槛，防把上一局残局误判成本局结束。
- `endTimer` + `cancelEnded()`：`reset` 事件或新请求到来时取消"准备退出"，否则会杀掉下一局。
- `configWatch`：`/status` 的 config 变化就打一行（行动限时/开局限时/回合上限/整局/耗时间/让过）。
- 蓝图里 `llm_chat` 的 `api_key` 为空时，从环境变量补（`DEEPSEEK_API_KEY` / `VMAF_LLM_API_KEY` / `OPENAI_API_KEY` …），密钥**不写进蓝图**。
- 会话落盘 `store.turn(...)`：`{v,session,seq,ts,kind:"turn",seat,requestId,rpcKind,round,blueprintHash,promptChars,estTokens,attempts,decision,latencyMs,ok,ctxSize,rejectReason,deadline}`；另有 `note` / `outcome` 行。
- 观测落盘 `live.turn(...)`：多了 `prompt / reply / reasoning / parsed / candidates / timings / runMs / plan`（观测台全靠它）。

**已知遗留问题**：同座位起两个 driver 会互相抢答（同一个 request 广播给该座位所有连接，先答者 200、后答者 404）。这不是协议 bug，但很容易复现"看起来像超时"的怪现象。清理方式见 11.7。

### 5.2 会话存储（`driver/lib/store.mjs`）

- **一局一文件**、**一行一回合**、append-only、不可变、字段只增不改。用 `fs.openSync(file,"a")+writeSync` 保证单写者原子追加。
- `summarizeTurns(rows,{maxTurns=30,maxChars=3000})` → 给"之前发生的事"段用的短摘要（`#92 r10 action {...} 7ms` 这种）。
- 设计取舍：不用 SQLite——单机单写者、每局几百行，JSONL 可 `grep`/`diff`/人读，O_APPEND 天然原子；将来要复用就把它抽成 HTTP 服务（**格式即接口**）。

### 5.3 备赛（开局前跑一次）

1. `--deck-code` 解码成 `{characters, cards}` → `POST /api/arena/deck`。
2. 拉**完整** catalog（牌组速览需要 hp/技能，不能用裁剪过的名字表）。
3. 跑 `blueprints/prep.json`（`shared = {deck, catalog}`）→ `plan_guard` 输出 ≤500 字战术。
4. 战术存进 `prep.plan`，之后**每一手**的 `shared.plan` 都带着它，进提示词 `### 赛前计划` 段。

实测：牌组 3 角色/30 张 → 计划 437~462 字、耗时 3.7~7.8s。

### 5.4 复盘（每回合末后台跑一次）

- 触发：一手决策开始时若 `roundNow > lastReviewRound`，说明"上一回合刚结束"，`void runReview({round: roundNow-1})` 在后台跑，不阻塞当前决策。
- 图形：`arena_input → state_brief / winrate_table → prompt_pack → llm_chat(deepseek-chat, temp 0.3, max_tokens 700) → review_parse`。
- 输出两行：`意图：…（≤200 字）` + `胜率：0.55`；存进 `prep.intent` / `prep.winrates[{round,winrate,intent}]`，并写 `store.note("review")`、`live.note({kind:"review"})`。
- 下一手的提示词会看到 `### 往期判断（自己估过的胜率与意图）` 段（由 `winrate_table` 渲染，含趋势）。实测每回合 1.8~2.1s。

### 5.5 观测台（`driver/tools/viewer.mjs`，`http://127.0.0.1:7810`）

- 传输：`GET /`（内联深色 HTML）、`/api/rows`、`/api/tail?n=`、`/api/stream`（SSE，500ms 轮询文件增量 + 15s ping）。

## 6. 蓝图详解（这是"策略"的全部）

### 6.1 决策蓝图 `blueprints/decide.json`（10 节点 25 边，线上 id `41ccb70bec8c`）

| 节点 | 类型 | 关键参数 | 作用 |
| --- | --- | --- | --- |
| `in` | arena_input | — | 把 `shared` 摊平成图字段：`request/detail/state/meta/retry/ctx/plan/deck/winrates/intent/config/catalog/summary` |
| `brief` | state_brief | `max_chars:1200, include_hand:true, include_opponent:true, include_raw:false` | 状态 → 中文战况（我方明细 + 对方公开信息） |
| `hist` | winrate_table | `keep:8, with_intent:true, intent_chars:60` | 往期胜率 + 意图 → 文本（含趋势） |
| `note` | json_pick | `key:"reason", default:""` | 把 422 的 `retry.reason` 取成字符串（否则类型预检不让接 `str`） |
| `rank` | action_rank | `top_k:8, style:"aggressive", keep_end_turn:true` | 候选打分 + 筛选 + 排序 → **注意：它同时是"菜单文本"的来源**（见 8.3 的坑） |
| `tips` | playbook | 11 个槽全空 | 分类别提示词槽（用户自己填） |
| `pack` | prompt_pack | `budget_chars:4000, role:"user", include_system:true, system:"先用较长的思路分析…最后只输出一个方括号里的编号数字", task:"从下面的可选动作里选一个最有利于获胜的。只回复一个数字。"` | 拼提示词（段落：memory → plan → deck → history → state → advice → menu → task → extra，超预算按优先级丢） |
| `llm` | llm_chat | `model:"deepseek-reasoner", api_base:"https://api.deepseek.com/v1", api_key:"", temperature:0.2, max_tokens:8192, timeout_seconds:90` | 调模型（`reasoning_content` 会被 driver 取出来给观测台） |
| `parse` | choice_parse | `mode:"auto", max_chars:500` | 回复 → 编号（容错 `"3"` / `"我选 1。"` / `"[0]"` / `{"index":2}`） |
| `build` | rpc_build | `allow_fallback:true` | 编号 → 完整 RpcResponse；非法时兜底（结束回合 → 第一个合法 → 0 号） |

关键连线（其余是 seat/catalog/detail 这类直连）：
```
in.detail → rank.detail        in.state → rank.state        in.seat → rank.seat
in.state/detail/seat/catalog → brief.*
in.retry → note.data           note.text → pack.extra
in.winrates → hist.history     hist.text → pack.history
rank.text → pack.menu_text  ★  in.plan → pack.plan    in.summary → pack.memory
tips.text → pack.advice        pack.messages → llm.messages
llm.reply → parse.text         rank.indexes → parse.valid_indexes
```

## 7. 关键设计决策（含"为什么"，改之前先读）

1. **驱动外置、策略在图里**：VMAF 节点是纯函数、一次跑完即散，没有"常驻等事件"的能力；所以"谁等、何时跑"放在 `driver/`，"怎么想"放在蓝图/插件。好处：改策略不碰时序，改时序不碰策略。
2. **司机不进任何 git 仓库**（放在 `整合2。0/driver/`）：`genius-invokation-dev` 要能继续 `update-upstream`，多一堆自己的文件会让合并很痛。
3. **座位自检做成硬失败（exit 3）**：用户上一次就是"连了 0、AI 在 1"导致整局 AI 不动，纯日志警告他看不见；退出码能让脚本/人一眼发现。
4. **决策节点自动取"蓝图汇点"**：不写死节点 id（写死过一次 `decide`，结果 30 次全兜底）。规则：`sinks = nodes - edge.sources`，唯一才采用，多个直接报错。
5. **本地再校验一次形状（`checkShape`）**：桥接的 `validateResponse` 只校验形状，不校验语义；一旦提交了形状不对的响应，游戏会判 `GiTcgIoError` 直接判负。所以宁可兜底也不提交坏响应。
6. **404 封存、422 重试**：404 意味着"这个 id 已经没了"（超时或被别人答了），再提交只会更乱；422 意味着"形状对但内容不合法"，pending 还在，可以把 `availableActions` 反馈回提示词重试（最多 3 次）。
7. **观测与对局解耦**：`live.mjs` 写文件失败要静默（观测绝不能影响对局）；viewer 是独立进程，挂了不影响下棋。
8. **存储与注入分离**：存储层 append-only（司机写事实：runId/deadline/422/latency），注入层每回合只给预算内一小包（图决定丢什么）。**写分两处、读只一处**。
9. **名字表按回合裁剪（`names.mjs`）**：整份 catalog 塞进图有 11 万字符，裁剪到本回合出现的 id 后约 3.4 万；`state_brief` 依然能翻译出全部中文名。
10. **密钥不进蓝图**：蓝图会被推到服务端、会被贴来贴去；用环境变量注入（`injectSecrets`），缺 key 只警告不崩（此时 `llm_chat` 是 dry_run）。
11. **reasoner 的 `max_tokens` 必须大**：思考会吃额度，2000 时正文为空 → 解析失败 → 全兜底（对着"AI 不动"的表象，根因在这里）。
12. **回合上限做成可选透传**：`ArenaConfig.maxRounds?` 未定义时**不传** `maxRoundsCount`，原版路径完全不变；这是"不改变原版玩法"约束的落实方式。
13. **"让过"与"耗时间"分离**：原来只有一个 stall（睡满限时），用户要的是"立刻过、不占时间"；两者语义不同，各留一个开关。
14. **`llm_chat` 必须 `asyncio.to_thread`**：`urllib.request.urlopen` 在 `async def` 里直接调用会阻塞事件循环，复盘和决策互相排队（实测平均 27s）。改完回到 1~2s。
15. **JSONL 而不是数据库**：单机单写者、几百行、要能 `grep` 和给人看；将来要共享再把 store 抽成服务（格式即接口）。

### 8.2 我核对了"到底有没有给重投/调和"

### 8.3 "提示词中毒"的证据（我在 `live.jsonl` 里抠出来的真实片段）

某一手的 `### 可选动作` 段，原样长这样：

```
【推荐行动】从 18 项里筛出 8 项（按进攻价值排序）
当前出战：闲云
选择 actions 里的 index；usedDice 可以省略，服务端会自动用该行动的 autoSelectedDice。
  [4] 元素调和（弃置 未知） ｜ 费用 1 ｜ removeEntity
  [8] 元素调和（弃置 未知） ｜ 费用 1 ｜ removeEntity
  [10] 元素调和（弃置 未知） ｜ 费用 1 ｜ removeEntity
  [12] 元素调和（弃置 未知） ｜ 费用 1 ｜ removeEntity
  [14] 元素调和（弃置 未知） ｜ 费用 1 ｜ removeEntity
  [15] 切换到 久岐忍 ｜ 费用 1 ｜ switchActive
  [16] 切换到 焚尽的炽炎魔女 ｜ 费用 1 ｜ switchActive
  [17] 结束回合 ｜ 费用 0
```

四个问题，一个比一个致命：

1. **只有 8 个选项**：`pack.menu_text ← rank.text`，而 `action_rank` 的 `top_k:8` **是过滤不是排序**。18 个合法选项里 10 个模型根本看不见。→ **这是"AI 选择面很窄、老是选 0 号"的最大结构性原因。**
2. **排在最前的是 5 个一模一样、信息量为 0 的"元素调和"**：`action_rank` 的打分只看 `preview` 里的 damage/heal/shield/energy，而调和的 preview 是 `removeEntity`（弃牌），**得分为 0**；0 分项按原编号排序，于是 4/8/10/12/14 这五个调和把前排全占了。真正有价值的技能/出牌（如果有分）反而被挤到后面甚至挤出 8 名。
3. **`（弃置 未知）`**：调和要弃哪张手牌根本没告诉他（`definitionId` 没被翻译）；`｜ removeEntity` 是内部预览类型直接漏进提示词。
4. **`选择 actions 里的 index；usedDice 可以省略，服务端会自动用该行动的 autoSelectedDice。`**：这是**写给我自己看的实现说明**，被 `action_rank` 当成 `hint` 塞给了模型。模型当然会困惑（它的思考里出现过"用户只给了一个可选动作？"这种自我怀疑）。
   另外 `playbook.footer` 和 `pack.task` 都在说"只回答一个数字"，重复了两遍。

**结论**：用户说"下毒"是对的——不是提示词写得太少，而是**这几句技术术语、"未知"占位、以及被砍掉的 10 个选项，把有效信息淹掉了**。修这个的收益，远大于"再多写两段战术文字"。

### 8.5 "耗时间/让过/知情"——已经查清并修好的部分

- **旧行为**：勾"耗时间"= AI 座位 `await sleep(限时)` 再交默认响应（烧绳），不是"立刻让过"。
- **真 bug**：`seatIoOptions()` 从来没把 `config` 传给桥接 → `GET /status` 的 `config` 恒为 `{}` → **agent 无法知情**。已修：页面开局 `pushConfig(configSnapshot())` → `POST /api/arena/state` 存 `config`；司机启动与配置变化时打印「行动限时/开局限时/回合上限/整局/本座位是否开耗时间/让过」，`stall`/`instant` 为真时各打一条"页面不会把请求发给 agent"的警告。
- **新增"让过"**（每座位一个）：立刻用默认响应，不占时间；与"耗时间"语义分离，UI 上有对照说明。
- **权限**：两个开关只能由页面设置（模型无法自行开启）。若将来要让模型"申请让过"，需要新增 agent→页面的通道（现在没有）。

### 8.6 用户对"体验"的其他隐性要求（从上下文推出来的）

- 演示时**要能看**（headful，不要纯无头）；用户经常在自己电脑上直接看那两个窗口。
- 每手延迟不能太难看：reasoner 每手 10–36s，一回合要几分钟，用户会以为"卡住了"（这也是他要流式的原因）。
- 任何"看起来 AI 不动作"的现象，先查 `/status` 的 `agents/pending`，再看 driver 日志的 `404/兜底`，**不要先怀疑模型**（历史上三次都是配置问题）。

### 9.3 P1：EvE 双模型日志 + 流式

- **双会话**：`viewer.mjs` 现在按 `session` 选一个文件。最省事的做法：`--two rv12-s0,rv12-s1`，左右两列各自渲染"列表 + 详情"；或者起两个 viewer 进程（7810/7811）并在页面里放 iframe——**先做前者**。
- **流式**：真正的流式需要三处配合：
  1. `llm_chat` 支持 `stream: true`（`urllib` 逐行读 `data: {...}`，把增量写进 `context` 或返回 `raw`；但 VMAF 节点是纯函数、`/run` 一次返回，**中间态没有出口**）；
  2. 因此更现实的做法是**司机直连模型的 SSE**（绕过 VMAF 的 `/run`）——但这会把策略从图里挪出来，违背 2.3 的设计；
  3. 折中：VMAF 加一个"流式旁路"——`llm_chat` 把增量 POST 到 driver 的一个 `/ingest` 端点（fire-and-forget），观测台从 driver 拉 SSE。**我倾向 3**：图不变，只是把"边想边写"当成副作用吐出来。
- 观测台侧的改动：`/api/stream` 已经是 SSE，加一种 `kind:"delta"` 行即可。

### 9.4 P2：每动作一句"自我提示"（用户点名要我想清楚）

两种做法，我给结论：**分两次输出更好**，理由是"自我提示"是给**下一手**看的，不应该和"这一手选几号"争夺同一次生成的注意力；而且分开后可以各自校验（编号必须合法，自省可以自由发挥）。

**推荐实现（同一次调用、两段输出 → 由解析器拆开）**：其实这是一个折中，代价最小：

```
请先写一行「留意：…」（不超过 60 字，写给下一手的自己：这手想达成什么、对手可能怎么应、
下一步优先做什么），然后单独一行只写一个方括号编号，例如 [3]。
```
- `choice_parse` 增加 `memo` 输出：取"留意："那行（没有就空）；
- driver 把它存进 `prep.memo`（最近 3 条），下一手塞进 `shared.memo`，`prompt_pack` 新增 `### 给自己的提醒` 段（受保护，永不丢）；
- 好处：**一次调用、不增加延迟**（reasoner 本来就要写思考）；坏处：模型偶尔会把两段写混 → 用 `choice_parse` 的容错兜住即可（现有的 `_BRACKET_RE` 已经能抓 `[3]`）。

如果用户坚持"两次输出"，就加 `--memo-call`：决策后再跑一次小图（`state_brief + last decision → llm(max_tokens 200) → memo_parse`），代价是每手多 1~2s。

### 9.5 P2：其他

- `replay.mjs --compare`：同一手用旧/新蓝图各跑一次，A/B 对比（调试台的关键功能）。
- `state_diff`：只给"跟上一手比变了什么"（省 token、也更聚焦）。
- 让 `winrate_table` 的 `keep` 可配（现在 8）。

## 11. 坑与教训清单（我踩过的，按"会让你浪费时间"排序）

1. **座位必须与 SSE 的 `?seat=` 一致**；`/agent/respond` 里没有 seat，由 `pending.seat` 决定归属。连错=永远收不到请求或替人类下棋。→ 已做硬失败自检。
2. **同一座位只能有一个 driver**：bridge 把 request 广播给该座位**所有**连接，先答者 200、后答者 404；表象像"超时"，实际是抢答。→ 用 `/status` 的 `agents` 数字一眼看穿。
3. **`/ai/log` 只回最近 500 条**（`lastSeq` 可续读但历史深处读不到），**不能**用来做逐请求审计；只有 driver 的会话 JSONL 可靠。
4. **`winner` 事件等不到**：`seatIo.ts` 靠 `flushAiEvents()` 在下一次请求时才推，结束时没有下一次请求。→ 用 `/state` 的 `phase===5`。
5. **`max_tokens` 太小会让 reasoner 的正文为空**（思考吃光额度）→ `choice_parse` 失败 → 全兜底。8192 起。
6. **蓝图路径**：`--blueprint blueprints/decide.json` 是相对 cwd 的，driver 用 `path.resolve`；现在有 `resolveInput` 兜一层，但**新写的参数别忘了**。
7. **`push-blueprint` 默认推 8000**（用户旧实例，只有 12 节点）→ 推成功但 8100 上没有 → 司机报"蓝图不可用"→ 全兜底。**永远显式 `--vmaf http://127.0.0.1:8100`**。
8. **`fetchRemoteBlueprint()` 返回文本**，直接塞进 `POST /run` 的 `blueprint` 字段会 422（`Input should be a valid dictionary`）→ 必须 `JSON.parse`（且要插在**复盘**分支，插在决策分支没用）。
9. **`urllib` 在 `async def` 里阻塞事件循环**：复盘与决策互相排队（平均 27s）。→ `asyncio.to_thread`。
10. **`review_parse` 的胜率正则会被全文里的数字污染**：`"胜率：0.55"` 曾被解析成 `0.04`。→ 只认"标签后 40 字符"或 `xx%` 或 `0.x`。
11. **`cost.dice` 是计数字典**（`{"0":2,"3":1}`），不是数组。
12. **`state` 里没有中文名**，只有 `definitionId`；对方手牌 `definitionId` 恒为 0。
13. **`8` 有两套语义**（费用=相同元素；骰面=万能）。
14. **弹窗不是对局进程**（没有 `window.theGame`）：它卡住/不同步**不影响对局**，但会误导人。→ `resyncPopup()` + "重新同步棋盘"。
15. **EvE 默认不弹窗**之后，若 `openPopup:false`，弹窗座位的 IO 必须给一个**静默 IO**，否则会等弹窗回应而挂住。
16. **`--keep-open` 不能用 `await new Promise(()=>{})`**：事件循环空了 Node 会以 **exit 13** 退出（顶层 await 未 settle）。→ `setInterval`。
17. **`label.parentElement.querySelector('input[type=checkbox]')` 会点到第一个"让过"**（三个 checkbox 同一行）→ 全兜底。→ 用 `label.nextElementSibling` 或取行内最后一个。
18. **页面 reset 会清空桥接里的牌组** → EvE 无法开局。→ driver 收到 `reset` 后重设牌组（已加）。
19. **`pnpm build "standalone..."` 会连带重建 state-editor 并撞上游既有 TS 错误**。→ `cd packages/standalone && npx vite build`。
20. **静态服务器每次请求读磁盘 dist**，所以重建后不用重启；但**改了 `local/arena/bridge.mjs` 必须重启**游戏服务。
21. **VMAF 插件热更新按 (mtime,size) 指纹**；改完打一次 `/health` 才注册（`/validate` 也触发扫描）。
22. **测试夹具断言"插件扫描无错误"**：任何插件语法错会让全量测试红。
23. **`report.results[i].output` 是模型实例**，不是 dict。
24. **类型预检拒绝 `Dict → str`**：需要 `json_pick`/`shared_get` 这类降维节点。
25. **`Field(description=...)` 里别用中文双引号**包 `"..."`（会把 Python 字符串切断，报语法错）。
26. **控制台是 GBK**：`curl | python` 读中文 JSON 会 `JSONDecodeError`，要用 `PYTHONIOENCODING=utf-8` 或直接 `urllib`。
27. **`ROOT` 用 `new URL(import.meta.url).pathname` 在中文路径下会变 `%E6%A1%8C...`** → `fileURLToPath`。
28. **不要动用户的 7717 与 8000**（他自己的副本与旧实例）。
29. **`/spectate` 会泄漏双方手牌/骰面**，只许调试。
30. **`--payload` 不是参数**（payload 默认就存，用 `--no-payload` 关）。
31. **`hint` 是给模型看的**：任何时候都别把"实现说明"写进 hint/menu（8.3 的教训）。
32. **观测台改完必须重启**（内联 HTML 在进程里）。
33. **`viewer` 的 `const` 别插进 `if (!t) { ... }` 分支**（我犯过：`reviewCard is not defined`，详情区空白）。→ `dbg-viewer.mjs` 能立刻抓到。
34. **Node 进程在本环境里用 `nohup ... &` 起会被 job runner 清掉**（表现为"日志停在某分钟"）。→ 用 DSH 的 `run_in_background` 托管，或确认进程独立存活。

## 14. 术语表

| 词 | 含义 |
| --- | --- |
| 桥接 / bridge | 游戏页面与外部进程之间的 Node 服务（`local/arena/bridge.mjs`），管 pending、SSE、日志、配置 |
| pending | 一次"等待外部回答"的请求记录（带 id、deadline、timer） |
| SSE | Server-Sent Events，桥接→driver 的单向事件流 |
| 司机 / driver | `driver/arena-driver.mjs`，负责"接请求→跑图→提交"的常驻进程 |
| 座位 / seat | 0=先手，1=后手；PvE 默认 AI 在 1 |
| 蓝图 / blueprint | VMAF 的 DAG（节点 + 边 + params），一次 `/run` 的输入 |
| 汇点 / sink | 没有出边的节点；driver 从这里取 `response` |
| 兜底 / fallback | 图失败或校验不过时，driver 自己给一个"最安全"的默认响应 |
| 直答 | `rerollDice`/`switchHands` 这类不需要编号的请求（观测台里标"直答"） |
| 备赛 / prep | 开局前跑一次，生成 ≤500 字战术 |
| 复盘 / review | 回合结束后跑一次，生成"意图 + 胜率" |
| aiDetail | 页面把 rpc 翻译成的"人类视图"（带中文名、费用、预示） |
| validity | 候选动作的可用性（0 合法，非 0 有具体原因） |
| 让过 / instant | 立刻用默认响应结束这一手（区别于"耗时间=睡满计时"） |
| 裁名字表 | 只把本回合出现的 id→名字塞进图，避免 11 万字符的目录全量进提示词 |
